# atari-mac

An emulator of the Atari 65XE home computer, written in Rust, for macOS.

## Status

The emulator boots AltirraOS and Altirra BASIC to the `Ready` prompt in a window, and you can
type BASIC programs. The work is done in vertical slices. The table below is generated by
`cargo run -p atari-harness --bin spec-index` (REQ-056), and a gate fails when it is out of
date. The requirement states are those of the traceability matrix: `tested` has a test that
runs, and `pending` has only planned test stubs.

## Scope

The target is an Atari 65XE with 64 KB of RAM, a 6502C CPU, ANTIC, GTIA, POKEY and a 6520 PIA,
in its NTSC and PAL versions. The emulator is exact to the CPU cycle.

These items are not goals:

- A Linux or Windows frontend. The core and the test harness build and run on Linux, but the
  frontend is for macOS only.
- Hardware outside the 65XE: extended memory (130XE), 65C02, 65C816, PBI devices and memory
  upgrades.
- The light pen, and the fifth player (`PRIOR` bit 4) of GTIA.

The full list of non-goals is in [docs/spec/README.md](docs/spec/README.md).

## Running

```sh
make roms                 # downloads the ROMs (one time)
cargo run --release       # opens the window: NTSC, BASIC enabled
cargo run --release -- --pal --scale 3
cargo run --release -- --bas examples/pong.bas
cargo run --release -- --bas examples/sounds.bas   # each SOUND distortion and pitch
cargo run --release -- --bas examples/audctl.bas   # the POKEY AUDCTL modes
```

| Option | Meaning |
| --- | --- |
| `--os <file>`, `--basic <file>` | Use other OS or BASIC ROM files (default: the files in `roms/`) |
| `--cart <file>` | Insert a cartridge: a raw image of 8 KB or 16 KB, or a CAR file (type 1, 2, 41 or 42) |
| `--xex <file>` | Start an executable (XEX): it boots from drive D1: with BASIC disabled (not with `--disk` or `--bas`) |
| `--disk <file>` | Insert an ATR disk image in drive D1: (the OS boots it at power-on) |
| `--pal` | PAL machine (default: NTSC) |
| `--scale <n>` | Window scale, 1 to 8 (default: 2) |
| `--artifacting` | NTSC artifacting filter: false colors for hi-res pixel patterns |
| `--pal-blending` | PAL chroma blending filter (needs `--pal`) |
| `--bas <file>` | Type the BASIC program in a text file at the `Ready` prompt, then `RUN` it |
| `--no-run` | With `--bas`: type the program, but do not `RUN` it |
| `--headless`, `--frames <n>`, `--screenshot <file>` | Run without a window for `n` frames, and save the last frame as a PNG file |

Keys: F1 inverse, F2 START, F3 SELECT, F4 OPTION, F5 RESET, F6 HELP, F7 BREAK, F9 pause,
F10 cold reset, the arrow keys and the left Option key for joystick 1, Command+Escape quit.
`cargo run --release -- --help` shows the full list.

## ROMs

The emulator uses free replacement ROMs: AltirraOS 3.11 and Altirra BASIC 1.59, by Avery Lee.
Their license permits distribution, but the repository does not contain them. Run `make roms`
to download them (see [roms/README.md](roms/README.md)). The emulator also accepts the original
Atari OS and BASIC ROMs, which you must supply yourself.

The repository contains no commercial software.

## Repository layout

| Path | Contents |
| --- | --- |
| `crates/atari-core/` | The emulator core: CPU, ANTIC, GTIA, POKEY, PIA, memory map and media. No dependencies. |
| `crates/harness/` | The test harness (`atari-harness`), the specification gates and the golden frame images |
| `src/`, `tests/` | The `atari-mac` frontend binary and its tests |
| `docs/` | Specification, design and plan |
| `docs/spec/references/` | The registry of the references and their section indices |
| `reference/` | The references that are in git: the HRM and the Atari 8-Bit FAQ, with their licenses in [reference/README.md](reference/README.md) |
| `scripts/fetch-roms.sh` | Downloads the ROMs, the test data and the pinned references, and verifies each file |
| `scripts/single-step-6502.sha1` | Checksums of the SingleStepTests 6502 suite |
| `.github/workflows/ci.yml` | The CI workflow |

These directories are downloaded and git ignores them: `roms/*.rom`, `test-data/` and
`reference/pinned/`. Git also ignores `reference/text/`, the place for text that you extract
from a PDF reference on your computer.

## Development

The toolchain is pinned in `rust-toolchain.toml`. `rustup` installs it automatically.

One-time setup:

```sh
make tools      # installs cargo-deny, cargo-hack, cargo-llvm-cov, cargo-machete, taplo, typos
make hooks      # enables the pre-commit hook in .githooks/
make roms       # downloads the ROMs and the small test data
make test-data  # also downloads the SingleStepTests 6502 suite (about 1.1 GB)
make reference  # optional: downloads the pinned references to reference/pinned/
```

Run every gate locally (the same gates as CI):

```sh
make check
```

| Gate | Tool | Command |

| Unit, integration and doc tests | cargo test | `cargo test --all-targets`, `cargo test --doc` |
| Docs build without warnings | rustdoc | `cargo doc --no-deps --document-private-items` |
| Advisories, licenses, duplicate dependencies, sources | cargo-deny | `cargo deny check` |
| Unused dependencies | cargo-machete | `cargo machete` |
| MSRV (`rust-version` in `Cargo.toml`) | cargo-hack | `cargo hack check --rust-version` |

| Line coverage of at least 80% | cargo-llvm-cov | `cargo llvm-cov --fail-under-lines 80` |
| Workflow lint and security (CI only) | actionlint, zizmor, shellcheck | — |

All warnings are errors (`RUSTFLAGS=-D warnings`). `unsafe` code is forbidden. To silence a
lint, use `#[expect(lint, reason = "...")]`. `#[allow]` is rejected.

### CI

CI runs on every push to `main` and on every pull request. The tests run on Linux and macOS.
The job `CI success` collects all results: use it as the required status check. A weekly run
finds new security advisories.

## How the work is done

Large tasks are split into independent parts. Each part is done in its own git worktree, then
merged and checked again. [CLAUDE.md](CLAUDE.md) gives the rules. In a new worktree,
`make worktree-setup` fast-forwards the branch to `main`, copies the ROMs and links `test-data/`
from the main checkout.

Each change follows this order:

1. A requirement in `docs/spec/` states the behavior, with exact acceptance criteria.
2. A design document in `docs/design/` states the interface and names the tests.
3. The code and the tests are written. Each test names the requirement that it verifies.

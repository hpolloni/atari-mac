# REQ-425: Priority mode 0 and conflicting priority bits

## Requirement

The emulator shall give the color results of HRM 6.7 for `PRIOR` bits 0-3 = `%0000` and for values with more than one of these bits set, including mixed colors and black.

## Rationale

Some programs use `PRIOR` = 0 to mix player and playfield colors. Wrong `PRIOR` values in programs must give the same display as the hardware.

## Acceptance criteria

1. With `PRIOR` = `$00`, `COLPF0` = `$40` and `COLPM0` = `$0A`, player 0 on `PF0` shows `$4A`.
2. With `PRIOR` = `$00`, `COLPF2` = `$70` and `COLPM2` = `$06`, player 2 on `PF2` shows `$76`.
3. With `PRIOR` = `$05`, player 0 on `PF0` shows `$00`.
4. With `PRIOR` = `$03`, player 2 on `PF2` shows `$00`.
5. With `PRIOR` = `$0C`, `COLPF0` = `$40` and `COLPM0` = `$0A`, player 0 on `PF0` shows `$40`.
6. A unit test checks each cell of the rows of HRM Table 16 without `P5` (PF01+P01, PF01+P01+P23, PF01+P23, PF23+P01, PF23+P23, PF23+P01+P23) for all 11 `PRIOR[3:0]` columns. In the table, PF01+P01 and PF01+P01+P23 share one row of cells. For each cell, the test sets `PRIOR` bit 4 = 0, uses player 0 for P01, player 2 for P23, `PF0` for PF01 and `PF2` for PF23, and gets `COLPM0`, `COLPM2`, `COLPF0`, `COLPF2` or `$00` for P01, P23, PF01, PF23 or black.

## Notes

These results follow from the equations in REQ-424. This requirement makes sure that the emulator does not simplify the equations.

GTIA-SPEC 3.0 and TRN HW-III.D/PRIOR state that more than one priority bit makes the objects with conflicting priorities black in the overlap region. They do not give the results for `PRIOR` bits 0-3 = `%0000`.

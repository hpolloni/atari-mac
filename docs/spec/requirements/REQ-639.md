# REQ-639: CAS tape images

## Requirement

The emulator shall load a CAS tape image that starts with a `FUJI` chunk, and shall make one tape block for each `data` chunk and each `fsk ` chunk, in file order, with the inter-record gap of the chunk and, for a `data` chunk, the baud rate of the last `baud` chunk before it, or 600 baud if there is no `baud` chunk before it.

## Rationale

CAS is the common image format for Atari cassette tapes (FAQ 9.1). A user can load a boot-tape game from a CAS file.

## Acceptance criteria

The test file T has these chunks, with no bytes between them. Each chunk has an 8-byte header: the 4-character chunk type, the data length (2 bytes, low byte first) and the aux value (2 bytes, low byte first). The data bytes follow the header. The file has 201 bytes.

| Offset | Header bytes | Data |
| --- | --- | --- |
| 0 | `46 55 4A 49 04 00 00 00` (`FUJI`, length 4) | `54 65 73 74` (`Test`) |
| 12 | `62 61 75 64 00 00 58 02` (`baud`, 600) | None |
| 20 | `64 61 74 61 84 00 20 4E` (`data`, length 132, gap 20000 ms) | The record R |
| 160 | `62 61 75 64 00 00 2C 01` (`baud`, 300) | None |
| 168 | `64 61 74 61 03 00 E8 03` (`data`, length 3, gap 1000 ms) | `55 55 AA` |
| 179 | `66 73 6B 20 06 00 64 00` (`fsk `, length 6, gap 100 ms) | `00 01 10 01 80 00` |
| 193 | `46 55 4A 49 00 00 00 00` (`FUJI`, length 0) | None |

The record R has 132 bytes: `55 55 FC`, then the 128 bytes `$00` to `$7F`, then the checksum `$87` (the carry wrap-around sum of the 131 bytes before it, REQ-616).

1. T loads with no error, with 3 tape blocks.
2. Block 1 is a data block with a gap of 20000 ms, 600 baud, and the 132 bytes of R.
3. Block 2 is a data block with a gap of 1000 ms, 300 baud, and the bytes `55 55 AA`.
4. Block 3 is a signal block with a gap of 100 ms and the signal lengths 256, 272 and 128 (in units of 0.1 ms). The first signal is 0.
5. The tape description is `Test`. The second `FUJI` chunk does not change the description and makes no block.
6. The file of the chunk at offset 0 and the chunk at offset 168 only (23 bytes, no `baud` chunk) loads with no error, with 1 data block of 600 baud, a gap of 1000 ms and the bytes `55 55 AA`.
7. The file T with 20 more bytes after it that are a `data` chunk of length 12 (`64 61 74 61 0C 00 00 00` and 12 bytes of `$00`) loads with no error, with 4 blocks. Block 4 has a gap of 0 ms, 300 baud and 12 bytes of `$00`.

## Notes

CAS-FMT gives the format: each chunk has an 8-byte header and `chunk_length` data bytes, all numbers are little-endian, and the file must begin with a `FUJI` chunk. CAS-FMT says that a `data` chunk holds "a standard tape record as read or written by Atari's SIO", normally 132 bytes that start with two `$55` bytes and end with a checksum, "however those are not necessary". Thus the emulator does not check the record contents. FAQ 7.1.6 gives the record of the OS cassette handler: two speed measurement bytes `$55`, a control byte (`$FC`, `$FA` or `$FE`), 128 data bytes and a checksum byte.

HRM C.2 says that the hardware does not need this framing: "The hardware only requires a baud rate in range with the correct FSK tones and supports an arbitrary bit stream". The HRM does not describe the CAS format.

The supported chunk types (`FUJI`, `baud`, `data` and `fsk `) are the decision of OI-048 (option 2, decided by the user on 2026-11-20). The turbo chunks (`pwms`, `pwmc`, `pwmd`, `pwml`) and other chunk types are errors (REQ-640). The CAS file does not hold the audio track (FAQ 9.1), so the tape has no audio.

The emulator reads the description as UTF-8 (CAS-FMT FUJI). A byte sequence that is not UTF-8 gives the replacement character, not an error. This is a project decision.

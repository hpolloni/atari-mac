# REQ-341: Memory refresh DMA

| Field | Value |
| --- | --- |
| Status | Draft |
| Priority | Should |
| Area | ANTIC |
| Source | HRM 4.14 Scan line timing (Memory refresh DMA); HRM 2.3 Memory system (Floating data bus, Memory refresh) |
| Verification | Test |
| Depends on | REQ-309 |

## Requirement

The emulator shall request nine refresh DMA cycles on every scan line, on cycles 25, 29, 33, 37, 41, 45, 49, 53 and 57, and shall move a request that playfield DMA blocks to the next free cycle.

## Rationale

Refresh cycles halt the CPU. The CPU speed and DLI timing are correct only with them.

## Acceptance criteria

1. With `DMACTL` = `$00`, `out.dma` is `Refresh` on cycles 25, 29, 33, 37, 41, 45, 49, 53 and 57 of every scan line of the frame, also on the vertical blank scan lines.
2. On the first scan line of a mode 2 line with `DMACTL` = `$22`, `out.dma` is `Refresh` on cycle 98 only. The request of cycle 25 waits until cycle 98, the first cycle with no other DMA, and ANTIC drops the requests of cycles 29-57.
3. On the first scan line of a mode 2 line with `DMACTL` = `$21`, `out.dma` is `Refresh` on cycles 25 and 90 only.
4. On each cycle where `out.dma` is `Refresh`, `out.halt` is set, and the fake `DmaMemory` gets no read.

## Notes

In wide character modes, the last refresh can move to cycle 105 or 106. This changes the `WSYNC` timing (REQ-336).

The HRM does not say which request is dropped when a request waits and a new request occurs. Project decision: the waiting request stays and ANTIC drops the new request.

Criteria 2 and 3 follow from the fetch cycles of REQ-309 and the refresh rule of this requirement. HRM 4.14 says that only 1-2 refresh cycles fit on the first scan line of modes 2-5. The DMA timing charts in the HRM are images, so the text copy of the HRM cannot confirm the exact cycles.

# REQ-410: PAL palette

## Requirement

The emulator shall convert each PAL color byte to RGB as in REQ-409, but with the chroma angle of hue H taken from the "Ideal UV angle" column of HRM Table 14.

## Rationale

The PAL GTIA uses different and uneven phases for the hues. A PAL palette is necessary for software made for PAL machines.

## Acceptance criteria

1. For each PAL byte with H = 1-15 and no channel outside 0-1 before the clamp, the inverse matrix of REQ-409 gives a chroma angle `atan2(V, U)` within 2° of the angle for H in this list: 135.0°, 112.5°, 90.0°, 67.5°, 45.0°, 22.5°, 337.5°, 315.0°, 292.5°, 270.0°, 225.0°, 202.5°, 180.0°, 157.5°, 135.0° (H = 1 to 15). It also gives Y within 0.01 of `L / 15` and a magnitude within 0.01 of 0.233.
2. `$00` gives (0, 0, 0), `$08` gives (136, 136, 136) and `$0F` gives (255, 255, 255), with no tolerance.
3. `$94` gives (5, 91, 114), `$1A` gives (218, 162, 85) and `$48` gives (199, 95, 182), with a tolerance of 1 for each channel.
4. For each luminance L, `$1L` and `$FL` give the same RGB value.
5. Each byte with H = 0 gives the same RGB value as the NTSC palette.

## Notes

Source: HRM Table 14 for the angles. The HRM gives no PAL saturation value, so the project uses `S = 0.233` as for NTSC (project decision). The HRM states that the ideal adjustment gives a sea-green GRAPHICS 0 screen and that real machines often use a delay of 18-19° per step (HRM D.4). An adjustable PAL model is an open issue.

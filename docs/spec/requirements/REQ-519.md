# REQ-519: Shift and Control keys

## Requirement

The emulator shall copy the Shift state into `KBCODE` bit 6 and the Control state into `KBCODE` bit 7 when a key press registers, and shall show the current Shift state in `SKSTAT` bit 3 (0 = down).

## Rationale

The OS uses `KBCODE` bits 6 and 7 to select the shifted and control characters. Some programs read `SKSTAT` bit 3 to detect Shift alone.

## Acceptance criteria

The setup is the setup of REQ-518.

1. With Shift down before the A key goes down, `KBCODE` reads `$7F` after the press registers. With Control down, it reads `$BF`. With Shift and Control down, it reads `$FF`.
2. When Shift goes down 10 x 114 cycles after the A key registered without Shift, `KBCODE` reads `$3F` for the next 300 x 114 cycles. When Shift goes up 10 x 114 cycles after Shift + A registered, `KBCODE` reads `$7F` for the next 300 x 114 cycles.
3. When Shift goes down with no other key down, `SKSTAT` bit 3 reads 0 within 65 x 114 cycles. When Shift goes up, `SKSTAT` bit 3 reads 1 within 65 x 114 cycles.
4. When only Shift, or only Control, is down for 300 x 114 cycles, `IRQST` bit 6 reads 1, `SKSTAT` bit 2 reads 1 and `KBCODE` does not change.
5. With `SKCTL` = `$02` (debounce off), criteria 3 and 4 give the same results.

## Notes

The HRM states that the scan detects Control together with scan code `$00` and Shift together with scan code `$10`. The two Shift keys are wired the same way. Software cannot tell them apart.

Control + Shift with a key code in `$00-$07` or `$10-$17` makes a phantom key on a real keyboard. The emulator does not emulate phantom keys. See the open issues in `docs/design/pokey.md`.

POKEY-SPEC 3 states that the scan does not debounce Shift, Control and BREAK.

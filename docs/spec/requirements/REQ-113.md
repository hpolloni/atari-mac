# REQ-113: KIL (JAM) opcodes

## Requirement

After a `KIL` opcode ($02, $12, $22, $32, $42, $52, $62, $72, $92, $B2, $D2, $F2), the emulator shall execute no instruction and no interrupt until a reset.

## Rationale

The KIL opcodes lock up the 6502 until reset (HRM 3.5). A program that crashes must show the same lockup as the real machine.

## Acceptance criteria

1. For each of the 12 KIL opcodes, the test `single_step_kil` passes: the bus accesses agree with the `cycles` list of the SingleStepTests 6502 file, and the registers agree with the `final` state.
2. Start: `$0200` = `$02`, `PC` = `$0200`. After the cycles of the SingleStepTests list, the CPU runs 1,000 more ticks. Each of these ticks makes one read of `$FFFF` and no write. `A`, `X`, `Y`, `S`, `P` and `PC` keep the values of the `final` state.
3. Start: as in criterion 2, with `I` = 0. The NMI line goes high and the IRQ line is asserted during the 1,000 ticks. The bus accesses are the same as in criterion 2: no interrupt sequence starts.
4. A machine executes a KIL opcode. Each later `run_frame` runs 29,868 machine cycles (NTSC), and the machine cycle counter advances by 29,868.
5. After a KIL opcode, `reset` starts the reset sequence of REQ-124. The CPU then fetches the opcode at the reset vector address.

## Notes

The HRM does not state the bus activity of a locked CPU. The SingleStepTests data shows reads of `PC`, `PC+1`, `$FFFF`, `$FFFE`, `$FFFE`, and then `$FFFF` in each cycle. The emulator continues the `$FFFF` reads (project decision).

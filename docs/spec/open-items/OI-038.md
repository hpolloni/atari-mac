# OI-038: POKEY to SIO bus serial interface

| Field | Value |
| --- | --- |
| Status | Decided |
| Area | POKEY, media |
| Affects | REQ-525, REQ-526, REQ-528, REQ-615 to REQ-622; pokey.md; media.md |
| Raised | 2026-11-19, integration check |

## Question

Which interface carries the serial data between POKEY and the SIO bus model?

## Context

The two designs disagreed. `pokey.md` had `SerialByte { value, end_cycle }`, a pull with `take_serial_byte`, and a line level input `set_serial_in`. `media.md` had its own `SerialByte { value, start, bit_cycles }`, a push with `host_byte`, and whole device bytes that the machine "gives to POKEY". The spec review found this after the open items were written.

## Options

1. Use one interface in both designs.

## Recommendation

Option 1.

## Decision

Decided on 2026-11-19 by the lead (an integration defect).

1. One type: `pokey::SerialByte { value, start_cycle, end_cycle }`. The SIO bus finds the bit length as `(end_cycle - start_cycle) / 10` (REQ-615 checks it).
2. Computer to bus: after the POKEY `tick` of each cycle, the machine moves each byte from `Pokey::take_serial_byte` to `SioBus::host_byte`.
3. Bus to computer: a line level. Before the POKEY `tick`, the machine calls `pokey.set_serial_in(sio.data_in_level(now))`. POKEY receives the bits with its own serial timing, as the hardware does (REQ-526, REQ-528).
4. `Pokey::cycle` and the SIO bus times both count machine cycles from power-on.

Changed: `pokey.md` (`SerialByte`, call contract, state), `media.md` (SIO bus interface, state, test method, open issue 1), `system.md` ("Timing").

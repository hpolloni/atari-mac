# OI-042: A second source shows that the HRM is wrong

## Question

When a second source shows that the HRM is wrong, does the requirement follow the HRM or the second source?

## Context

OI-041 says that the HRM is correct when two references do not agree. Before OI-041, some requirements already followed other evidence where the HRM is wrong, and OI-024 says: "The requirements already follow the correct values." Examples:

- REQ-112 (SHA): HRM 3.5 says the stored value uses "the high byte of the base address as read from page zero, not the high byte after Y has been added". NMS `SHA` gives `A & X & (H+1)`, and SST agrees. REQ-112 follows SST.
- REQ-108: HRM 3.2 says "6 is added if the nibble result exceeds 10". Its own example and NMS `decimal-nutshell` need "exceeds 9". REQ-108 follows the example.
- REQ-326: HRM 4.6 says that each display list fetch depends on the DMA state in its own cycle ("late enough for the instruction byte fetch to be suppressed but early enough for the address fetches to occur"). REQ-326 and the code use the instruction fetch of cycle 1 for the address fetches too. No second source covers this case. Here the requirement does not follow the HRM, and no source says that the HRM is wrong.

## Options

1. The HRM always wins. REQ-108 and REQ-112 change to the HRM text, and REQ-326 changes to HRM 4.6.
2. The HRM wins, except where an open item records an HRM error and you decide for the other source. REQ-108 and REQ-112 stay. REQ-326 changes to HRM 4.6, because no source says that the HRM is wrong there.
3. Each conflict is an open item, and no default applies.

## Recommendation

Option 2. SST is a record of real hardware, so REQ-112 is correct as it is. The rule stays simple, and you decide each exception.

## Decision

Not decided.
